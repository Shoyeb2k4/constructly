# Android signing

Status: **no production keystore exists yet.** Release builds currently produce
`app-release-unsigned.apk`, which will not install on a phone and cannot be
uploaded to Play. Creating the key is a deliberate, human decision — see
[Creating the upload key](#creating-the-upload-key) — because the identity it
establishes is effectively permanent.

---

## The two keys, and why the distinction matters

Google Play Console uses **Play App Signing**, which splits one credential into
two. Confusing them is the single most common way a team loses the ability to
ship.

| | **App signing key** | **Upload key** |
|---|---|---|
| Signs | the APKs Google delivers to devices | the AAB you upload to Play |
| Held by | Google, in their key store | you, on your machine and in CI |
| Seen by devices | yes — this is the app's identity | never |
| If lost | **the app can never be updated again** | recoverable: Google resets it |
| If leaked | catastrophic, unfixable | bad, but rotatable |

When you first enable Play App Signing, Google can **generate the app signing
key for you** and keep it. That is the recommended path: the irreplaceable key
lives somewhere with better custody than a laptop, and the key you actually
handle — the upload key — is the recoverable one.

**The practical consequence:** the keystore this document tells you to create is
an *upload* key. Losing it is an inconvenience (email Google, get it reset), not
an extinction event. That is exactly why it is the one we hold.

### Direct-install APKs are a separate case

An APK you sideload for testing (Stage A) is signed with the upload key and
installed as-is — Play is not involved, so there is no app signing key in the
picture. This matters in one practical way: **a device that installed a
directly-signed APK cannot later install the Play version over the top**, and
vice versa, because the signatures differ. Testers move between the two by
uninstalling first, which wipes local app data.

## Creating the upload key

> **Do this yourself.** It creates a credential; it should not be generated by
> tooling that then knows the password. Run it on the machine that will hold the
> key.

```bash
keytool -genkeypair -v -keystore constructly-upload.jks -alias constructly-upload -keyalg RSA -keysize 4096 -validity 10000
```

Notes on the arguments, since each is hard to change later:

- **`-validity 10000`** (~27 years). Play requires a key valid past 2033. A
  shorter validity means a forced key migration later.
- **`-keysize 4096`** — 2048 is accepted, 4096 costs nothing here.
- **`-alias`** — you must supply this on every build. Pick something you will
  recognise in a year.

`keytool` will ask for a keystore password, a key password, and a distinguished
name. Use a password manager; these are not values to invent at the prompt.

### Where the file goes

**Never inside the repository.** `android/.gitignore` refuses `*.jks`,
`*.keystore`, `*.p12` and `keystore.properties`, and
`npm run verify:signing` fails the build if signing material is ever tracked —
but the reliable protection is keeping the file somewhere else entirely.

Store it in:

1. Your password manager (as an attachment), **and**
2. An offline backup you control.

If you lose every copy of the upload key you can recover — Play will reset it —
but only after a support round-trip, which is not something to discover during
an urgent release.

## Local builds

Create `android/keystore.properties` (gitignored):

```properties
storeFile=/absolute/path/to/constructly-upload.jks
storePassword=…
keyAlias=constructly-upload
keyPassword=…
```

Then:

```bash
npm run mobile:sync:android && npm run android:apk
```

Gradle prints which source the signing config came from, and never prints the
alias, the path or any password. If no signing material is found it says so and
leaves the artifact unsigned rather than falling back to the debug key — a
debug-signed "release" installs and looks completely normal, but can never be
updated by a real release.

## CI builds

The workflow reads four secrets and materialises the keystore for the duration
of the job:

| Secret | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | `base64 -w0 constructly-upload.jks` |
| `ANDROID_KEYSTORE_PASSWORD` | keystore password |
| `ANDROID_KEY_ALIAS` | `constructly-upload` |
| `ANDROID_KEY_PASSWORD` | key password |

Add them under **Settings → Secrets and variables → Actions → Secrets**. Never
as *Variables* — variables are printed in logs.

## Verifying a signed artifact

Signing is easy to believe you have done. Check:

```bash
# Which key actually signed it, and with which schemes
"$ANDROID_HOME/build-tools/36.0.0/apksigner" verify --print-certs --verbose app-release.apk
```

Confirm the SHA-256 fingerprint matches the key you intended. For an AAB:

```bash
keytool -printcert -jarfile app-release.aab
```

A release build that produced `app-release-unsigned.apk` is **not signed**,
regardless of what any other step reported.

## Rotating a leaked upload key

If the upload key is exposed:

1. Generate a new keystore (above).
2. Play Console → **Test and release → Setup → App integrity → Upload key →
   Request upload key reset**, attaching the new key's certificate
   (`keytool -export -rfc -keystore new.jks -alias … -file upload_certificate.pem`).
3. Google switches the accepted upload key, usually within a couple of days.
4. Replace the CI secrets.

Users are unaffected: the *app signing* key never changed, so updates continue
to verify on device. This is the whole reason the two-key split is worth having.
